# Project setup

Respond and write user-facing setup documents in the user's language. If the user
communicates in Spanish, use Spanish for the conversation, `project-profile.md`,
the approved `AGENTS.md` integration block, and any optional documents created
from the bundled models. Keep canonical identifiers, filenames, commands, API
names, and quoted source text unchanged. Ask only if the user requests a different
language or the project has an explicit documentation-language convention; in
that case, follow the project's convention and record it in the profile. Do not
translate skill names, agent names, code, or existing project documents.

Require a direct human request to set up or refresh this project's workflow. Read `references/setup-modes.md` and select new-project or existing-project mode from repository evidence and the user's request. Check `references/client-compatibility.md` before promising discovery, delegation, or portability. If unclear, ask which project directory is the target. Offer two input routes: answer in chat, or complete `assets/project-brief.example.md` and place it at the target root as `project-brief.md`. Read `references/input-review.md` before using either route. Early in setup, ask whether the installed agents, skills, and profile should be versioned in this repository (default) or kept local through Git ignore rules; verify the actual Git state before applying the choice. Inspect before writing. If `project-profile.md` already exists, compare it with current evidence and preserve intentional project decisions; update only verified drift or decisions the user changes. If it is partial or conflicts with repository policy, ask about the specific ambiguity before overwriting anything.

For an existing project, read `AGENTS.md` if present, requirements, architecture, task tracking, package and build manifests, lockfiles, source layout, tests, lint and format configuration, CI, security policy/threat model (`SECURITY.md`, security docs), and Git state. For a new project, collect the intended product, stack, scope, checks, and working constraints from the user; label planned technologies as planned rather than detected. Use `references/technology-detection.md` and `references/skill-inventory.md` to discover skills visible in the current environment, assess fit and conflicts, and propose missing coding-style guidance. Do not infer product rules or permissions from a framework name.

Evaluate the six bundled technical skills with the same compatibility and conflict checks as environment skills. Select only those relevant to the assigned task. For a missing domain skill, collect explicit project rules and examples before proposing creation; do not claim generated guidance was evaluated without evidence.

For project-specific domain guidance, follow `references/domain-skill-authoring.md`. Offer reuse or creation with the chosen name and target path; accept rules and examples through chat or `assets/domain-brief.example.md`. Use `assets/domain-skill.example.md` for confirmed content, validate its quality and record evidence before activating it. Keep incomplete drafts outside skill discovery and preserve generated domain skills as project-owned files.

Build a draft from `assets/project-profile.example.md`. Review user-supplied files and chat answers against repository evidence, flagging contradictions, missing decisions, and concrete improvements with file references. Do not silently rewrite the user's requirements, architecture, or roadmap. For each technology, record evidence paths and matching skills, their source, availability, and intended use. Recommend missing skills with a narrow purpose and reason; do not install dependencies or third-party skills during discovery, or invent available skill names. Creating the domain skill explicitly selected by the user is the narrow exception governed by `references/domain-skill-authoring.md`. Present incompatible or overlapping instructions with their sources and practical effect, then ask the developer to choose; never silently decide a policy conflict. Ask the user only for purpose, scope, acceptance, task tracking, parallel limits, or other decisions that repository evidence cannot settle. Mark unresolved items explicitly and do not claim the profile is ready while required fields remain open. When validating the pack itself or an adapter change, use `references/evaluation-scenarios.md`.

Keep the conversation lightweight. First present a short setup summary with: detected project mode, what you found, the few missing decisions, and recommended defaults. Ask blocking questions together in one compact message. Use defaults only for reversible workflow preferences (serial execution, current client permissions, no extra agents); explain that parallelism is opt-in and depends on verified client support. Do not ask the user to choose model names, token budgets, agent depth, or concurrency numbers unless the project has a concrete need. Put detailed evidence, skill inventory, conflicts, and optional tuning in `project-profile.md` or a follow-up section, not in the initial question. Surface product-scope and instruction conflicts prominently because they require a human decision.

Offer the optional requirements, architecture, and roadmap models through `references/input-review.md`. The user may select any subset for creation during setup, supply equivalent documents, or defer them. Create only the selected files at agreed paths, preserve existing sources, and record their canonical locations in the profile.

Use `references/optional-documents.md` to offer coordination models (work plan, execution state, review report) and specialist models (threat model, test strategy, architecture decision) only when relevant. All are optional; show a short recommendation, not a mandatory questionnaire. Record selected paths and writing ownership in the profile. Preserve the approval and read-only role boundaries when using these models later.

After the required decisions are known, write `project-profile.md` at the target root. Re-read it and verify observed paths, commands, skill names, and discovery of the installed agents and skills. If there is no `AGENTS.md`, offer to create a minimal project entry point that directs Codex to invoke `$team-workflow` automatically for implementation, bug-fix, and refactor requests in this repository; do not create it until the user chooses. If one exists, propose a small additive rule with the same trigger and preserve all existing instructions. Mark planned paths and commands that cannot yet be verified. Apply the chosen visibility only to this workflow's installed files and profile, following `references/setup-cleanup.md`; never claim Git ignore hides tracked files. Report the mode, observed or planned technologies, selected, unavailable and proposed skills, conflicts and decisions, and remaining limits. Do not create application code, change agent definitions, or store secrets as part of setup. The only permitted `AGENTS.md` edit is the exact additive block the user approved; preserve all other content and avoid duplicate blocks. Use `assets/AGENTS-workflow.example.md` for that block. Starting implementation requires a separate approved `$team-workflow` plan.

At the end, follow `references/setup-cleanup.md`. If the original template directory is inside the target repository, offer its deletion, an exact Git ignore rule, or keeping it. Wait for the user's choice and apply only that choice after checking that the installed copies are complete. This cleanup concerns the source template directory, not the installed agents or skills.

Use `references/maintenance.md` for install verification, updates, and removal. The shell entry point requires Bash and Python 3.9+; alternatively run the Python entry point directly. When Codex does not discover the newly installed files, ask the user to open a fresh Codex session at the project root and verify discovery before claiming setup succeeded.
