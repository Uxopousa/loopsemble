# Security review workflow

Use `security-reviewer` for changes affecting trust boundaries, authentication or authorization, sensitive data, user-controlled parsing/rendering, external integrations, secrets, dependencies, deployment/configuration, or when the user requests a security review. If the regular Reviewer discovers a plausible security risk during review, the coordinator pauses completion and delegates that finding and its affected paths to `security-reviewer`, even when the specialist was not in the initial plan. For low-risk changes with no security-relevant surface, the regular Reviewer may cover obvious regressions without a separate security agent.

1. Read applicable security policy, threat model, architecture, plan, and diff. Identify assets, attacker starting position, entry points, trust boundaries, sensitive operations/data, and changed security controls. Treat missing threat context as a limitation; infer no organizational policy.
2. Review only the approved scope and affected paths. Trace attacker-controlled data through validation and sinks. Check authorization at the operation boundary, data isolation, secret handling, injection/output encoding, unsafe external requests, dependency/configuration impact, failure behavior, and abuse/resource limits as relevant.
3. Static tools may guide review when already configured. Confirm findings in the code and reason about reachability and impact. Do not install scanners, scan external targets, exploit production systems, or expose secrets without explicit approval and suitable authorization.
4. Report findings with file/line, attacker preconditions, exploit scenario, violated security property, impact, severity, confidence, and actionable fix/verification. Separate confirmed defects from questions and assumptions. List reviewed areas, exclusions, unavailable tools/context, and residual risks; never call a scoped diff review a full penetration test or security certification.
5. The security specialist is read-only. The coordinator triages findings. The approved Developer fixes accepted findings within the approved scope; the security specialist rechecks the security fix, while the independent Reviewer checks broader integration. If remediation expands scope or changes product/security policy, pause for human approval before editing. A dispute returns to the user.
